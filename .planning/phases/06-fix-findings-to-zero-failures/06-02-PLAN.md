<task type="auto">
  <name>task 1: Guard secret generation and provisioning against xtrace</name>
  <files>scripts/_common.sh, scripts/install</files>
  <action>
    Prevent `set -x` (xtrace) from echoing expanded secret values during install/upgrade. The harness enables xtrace; the package must suppress it around lines that expand secrets.

    1. In `scripts/_common.sh`, wrap the body of `librechat_generate_secrets()` (lines ~59-75) with an xtrace guard. Use the portable idiom:
       ```
       local xtrace_was_on=false
       case $- in *x*) xtrace_was_on=true;; esac
       set +o xtrace
       ... existing ynh_string_random / ynh_app_setting_set calls ...
       [ "$xtrace_was_on" = true ] && set -o xtrace
       ```
       This keeps generation + persistence behavior identical while preventing `admin_panel_secret=...`, `admin_password=...`, `jwt_secret=...`, `jwt_refresh_secret=...`, `meili_master_key=...` from being xtrace-echoed.
       Preserve the function's outputs (the shell variables must still be set in the caller — do NOT run the assignment in a subshell).

    2. In `scripts/_common.sh`, `librechat_regen_and_merge_configs()` (upgrade path) reads secrets at lines ~124-128 via `ynh_app_setting_get`. Guard those read-backs (and the missing-setting validation loop ~131-135) with the same xtrace suppression so upgrade logs do not echo persisted secret values.

    3. In `scripts/install`, guard `librechat_create_admin_user "$admin_email" "$admin_password"` (`scripts/install:124`) — the call passes the password as argv, which xtrace echoes. Wrap with the same suppression idiom. Do NOT alter the call's arguments or behavior.
       Also audit for any other secret-bearing expansion in `scripts/install` (none expected beyond the password display in Step 11, which is INTENTIONAL).

    4. KEEP exactly one intended admin-password display: `ynh_print_info "Admin password: $admin_password"` (`scripts/install:145`). Do NOT remove it (locked: operator needs it). The `mail` heredoc at lines 132-142 also intentionally contains the password for the operator's email; leave it — it is not xtrace output. Ensure the password is not *additionally* echoed (e.g. do not add debug prints).

    Do NOT add a blanket `set +x` at the top of any script (that would suppress all xtrace debugging, which the harness may rely on). Scope guards narrowly to secret lines.
  </action>

<task type="auto">
  <name>task 2: Build the archived-log redaction tool</name>
  <files>scripts/redact_pc_logs.sh</files>
  <action>
    Create `scripts/redact_pc_logs.sh` — a Bash tool that redacts real secret values from archived `package_check` logs and asserts the result is clean.

    Requirements:
    - Usage: `bash scripts/redact_pc_logs.sh <input-dir-or-file> [<output-dir>]` (default output: sibling `<name>.redacted`).
    - It takes a set of secret values to redact, supplied via a file or env (e.g. `SECRETS_FILE` with one `KEY=VALUE` per line, or a list of values). Rationale: the real values are recoverable from the run's app settings / the raw debug log; the operator supplies them. Support `SECRETS_FILE` and, as a fallback, a comma/space-separated `SECRET_VALUES` env var.
    - For each value, replace every occurrence in each input log with `***REDACTED***` (use a literal, non-regex replacement — escape regex metacharacters; skip empty values).
    - Idempotent: re-running over already-redacted files is safe.
    - After redaction, **assert** that none of the supplied values appear in any output file; print `REDACTION OK: 0 residual secret matches` and exit 0, or list residuals and exit 1.
    - Also provide a pure assertion mode (`--assert-only`) that checks a directory without rewriting, for pre-commit verification.
    - `set -euo pipefail`; no hardcoded secrets; do not print secret values (print only key names / match counts).

    This tool is used for the POLS-01 archive (Plan 05) and can also audit the raw logs anytime.
  </action>
